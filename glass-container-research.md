# Research: Prior Art for the "Glass Container" Project-Progress Tracker

## 1. What pattern this fits into

This concept sits at the intersection of three categories that normally stay separate: a **status dashboard** (like a developer portal), a **change gate** (like CI/CD or feature flags), and an **AI-tool interface layer** (like an MCP server in front of an agentic IDE). Nothing in the research below combines all three for a *single developer's own personal projects* — the closest analogues are all built for teams, and all of them pay a real cost for the surface area teams need but you don't. The honest positioning is: **a personal, gated source-of-truth for AI-assisted solo projects** — closer to "a Backstage catalog entry with a lock on the write path" than to any of the named tools individually.

## 2. Comparable systems: what to borrow, adapt, avoid

### Developer portals — Backstage and its ecosystem

Backstage's core idea — a catalog of entities with structured metadata as the shared source of truth — is exactly your "manifest per project" instinct, and it's proven at scale. But its adoption data is a direct warning. Outside Spotify itself, external organizations see roughly a 10% adoption rate against Spotify's internal 99%, and analysts attribute the gap to complexity and the absence of a clear prioritization signal — <cite index="3-1">developers get overwhelmed by the sheer volume of data presented without proper alerting or task management</cite>. The catalog is only as good as the metadata behind it, and that metadata rots fast: <cite index="2-1">Backstage catalogs are driven by static YAML files that developers are expected to maintain manually, and because developers don't like maintaining metadata, catalogs go stale and trust in them collapses</cite>. Analysts also note the plugin model doesn't fix this — <cite index="3-1">plugins don't solve the fundamental data-model and manual-maintenance problems</cite>, and in practice <cite index="2-1">plugins often feel like separate bolted-on widgets rather than one integrated experience</cite>. One production-deployment retrospective is blunt that <cite index="6-1">most Backstage failures are adoption failures, not technical failures, and that avoiding feature overload matters more than avoiding technical bugs</cite>.

- **Borrow:** the entity/manifest-as-source-of-truth idea; treating the catalog as a product with its own trust budget.
- **Adapt:** replace "developer manually edits YAML" with "the MCP write tool is the *only* path that updates the manifest" — this removes the exact failure mode (stale, hand-maintained metadata) that killed Backstage's trust for most adopters, for free, as a side effect of your compatibility-gate design.
- **Avoid:** a fixed, generic entity schema and a plugin marketplace mindset. Your per-project stage model already avoids Backstage's "fixed set of entity types" problem — <cite index="2-1">Backstage works with a fixed set of entity types like Components, APIs, Systems, and Resources, which is fine only if your engineering world maps neatly onto that model</cite>. Don't let scope-creep pull you toward a general catalog; the 5-project cap is doing real work here and should stay.

### CI/CD gates and pre-commit hooks

This is the most directly relevant prior art for your compatibility gate, and the community has a hard-won, fairly convergent opinion: **local/fast gates and authoritative/slow gates are different things and conflating them is the single most common mistake.** One practitioner's postmortem captures the mechanism precisely: <cite index="19-1">slow hooks get bypassed — if a pre-commit hook takes 30 seconds, developers will reach for the flag that skips it</cite>, so the fix is to <cite index="19-1">run only fast, objective checks locally and move slower checks or subjective judgment calls to a later, non-bypassable stage</cite>. A monorepo lead's regret post makes the failure mode visceral: heavy local gates on every commit created constant multi-second waits and a workflow that felt adversarial rather than protective, to the point where the writer's advice is to let the authoritative check happen once, later, and keep the local layer light. The countervailing, more defensive view is worth noting too — one engineer argues aggressive local pre-commit enforcement is itself <cite index="24-1">a disguised form of distrust in your own workers</cite> — which is a useful gut-check on tone: a gate that reads as "the tool doesn't trust you" will get routed around even when it's technically correct.

Two structural lessons map directly onto your layered gate:
- **Speed budget per layer.** Layer 1 (build/tests) is exactly the kind of thing that must stay fast or it gets skipped — this argues for running it incrementally/cached rather than a full rebuild on every `validate_change` call.
- **Escalating authority, not escalating friction.** The recurring pattern across every source is: fast/local catches the *obvious*, slow/authoritative is the actual gate. Your `record_progress` requiring explicit human confirmation *every time* already encodes this correctly — it's the CI equivalent of "protected branch," and it should stay non-negotiable even once all three gate layers exist, exactly as you've decided.
- **Borrow:** tiered enforcement (fast local check → authoritative check before state changes).
- **Adapt:** "block vs. warn" as a per-layer, not per-check, decision — e.g., layer 1 (build/tests) can hard-block, while layer 3 (schema/type validation) might reasonably start as warn-only while you calibrate false-positive rates, before graduating to block.
- **Avoid:** stacking all three layers as blocking from day one before each is individually trustworthy — this is precisely the trap that turns a gate into something developers stop respecting, per the monorepo account above. Your explicit "layer 1 stable before layer 2 activates" plan already avoids this; keep it.

### Feature flags / progressive rollout (LaunchDarkly-style)

The transferable idea isn't the UI, it's the **separation between exposure control and rollback speed**. LaunchDarkly's own framing distinguishes exactly three reusable mechanisms: <cite index="31-1">progressive exposure via canary and ring rollout, and emergency reversal via a kill switch — these are not interchangeable, since each answers a different question about risk</cite>, and critically, <cite index="31-1">rollback speed is a property of *where* the check is evaluated, not what kind of check it is</cite>. The most relevant idea for your snapshot service is the automated-guardrail pattern: <cite index="35-1">the platform can automatically advance a rollout stage when metrics stay within bounds, and automatically dial back to zero — an automatic kill switch — the moment a metric breaches its guardrail</cite>. This is a clean template for "snapshots fire automatically because they're additive," while writes to permanent state stay manual — you've essentially already re-derived LaunchDarkly's exposure/rollback split independently, which is a good sign.

- **Borrow:** the kill-switch mental model for your snapshot/rollback service — a snapshot is only trustworthy if restoring from it is as close to instant and as low-ceremony as a flag flip.
- **Adapt:** the "guardrail breach → automatic reversal" pattern could apply to your compatibility gate's *snapshot* trigger (snapshot automatically before any layer-3 schema change is attempted, not just on a timer), even though the *state write* itself stays human-gated per your fixed decision.
- **Avoid:** LaunchDarkly's own complexity ceiling — <cite index="35-1">as flag count grows into the thousands without governance, teams accumulate technical debt and inconsistent practices</cite>. At 5 projects with per-project stage lists this is a low near-term risk, but it's the reason to keep stage/flag definitions declarative and reviewable rather than letting them multiply implicitly.

### Task boards — Linear vs. Notion vs. GitHub Projects

This is your most important adoption research, because it's the closest analogue to "will the human actually update this." The comparisons are unusually consistent on *why* Linear gets kept and Notion gets abandoned for tracking, even though Notion is more flexible. The mechanism is friction-per-update, not feature count: <cite index="46-1">when updating a ticket requires many clicks and slow reloads, that friction causes people to stop using the tool entirely and fall back to verbal status updates instead</cite>, whereas <cite index="46-1">if the tool is fast enough that updating status takes a single keystroke, the tool itself becomes the source of truth</cite>. The speed difference is architectural, not cosmetic — <cite index="42-1">Linear is built as a local-first client that syncs to the server, so interactions feel like a native app rather than a web tool, and for a tracker engineers touch dozens of times a day that cumulative low-latency feedback fundamentally changes usage patterns</cite>, while <cite index="42-1">Notion's database views carry visible, growing latency as record counts increase, which is tolerable for docs but corrosive for a tool meant to be touched constantly</cite>. Notion's own abandonment pattern is instructive about scope: <cite index="38-1">Notion's flexibility means users spend more time learning and configuring than getting work done, and its "layered versatility" can become a system that consumes more time than it saves for basic personal use</cite>. One long-time user's retrospective adds a sharper detail: most of a three-year Notion workspace turned out to be unused — <cite index="41-1">after archiving the full workspace and migrating only the ~30% actually in use, the writer never went back to the archive once</cite>, which is a strong argument for shipping with almost nothing configurable at first.

- **Borrow:** single-keystroke/command-palette-style update paths; local-first responsiveness as a design requirement, not a nice-to-have.
- **Adapt:** since your primary "update" event should mostly be the AI calling `record_progress` after a human confirms — not a human manually dragging cards — the Linear lesson translates to: **make the confirmation step itself the single point of friction, and make it fast** (one dialog, one keystroke, not a form).
- **Avoid:** Notion's everything-is-configurable trap. Per-project custom stage lists are already a deliberate, bounded flexibility; resist adding freeform fields, tags, or views beyond what the cylinder metaphor needs.

### Agentic IDEs — Cursor, Windsurf, Antigravity, Devin, Replit Agent

This is the category the developer specifically flagged, and the research is unusually candid about *why* these feel heavy even to people who like them. Antigravity is the most instructive because reviewers keep landing on the same two-sided verdict: it's genuinely more legible than a raw chat loop, but the legibility itself has a cost. On the positive side, its "artifacts" design is a real answer to opacity — <cite index="16-1">showing raw tool logs drowns developers in noise, and showing only a final diff makes decisions unauditable, so the system instead surfaces structured artifacts (plans, task lists, screenshots, recordings) that a developer can comment on like a shared document</cite>. That's close in spirit to your "meniscus line + colored dots" idea: a compressed, glanceable signal instead of a raw log. But the tone shift required is real: <cite index="13-1">the paradigm assumes you already know what you want upfront, and without that clarity the agent can become confidently wrong or overly rigid — in those cases classic exploratory human-led work still wins</cite>, and one hands-on reviewer's blunt summary is that the tool currently behaves like <cite index="12-1">a talented but inexperienced junior developer — fast, occasionally reckless, and in need of supervision, requiring you to keep version control tight</cite>. There's also a documented real-world failure mode worth taking seriously given your own history with Skiba Tables: <cite index="13-1">there have already been reports of security risks like prompt injection and file exfiltration, including one notable incident of destructive file deletion through the agent's terminal access</cite> — direct evidence for why your MCP server exposes a *fixed, limited tool set* rather than shell access, and why `record_progress` needs a human in the loop every time.

The complexity complaint specifically (not the capability complaint) tends to be about **surface area**, not depth: multiple concurrent agent threads, a Manager View, per-task model switching, browser automation, cron-scheduled agents, and a settings screen just to turn off terminal access — <cite index="17-1">the product markets itself as a command center running agents in parallel across folders with project-level settings, bounded access, and persistent permission trust</cite>. Every one of these is individually reasonable, but together they add up to a tool where a solo/non-professional user has to learn an operating model before getting value — which is precisely the complaint the developer raised about VS Code and Antigravity.

- **Borrow:** the artifact/plan-review pattern (a structured, human-legible summary of what changed and why, reviewable before it's committed to state) — this maps directly onto what your compatibility-gate rejection dot should show a human: not a raw diff or log, but a short structured explanation.
- **Adapt:** Antigravity's per-task risk-tolerance idea — <cite index="16-1">the tool adapts its autonomy level to the task's risk rather than using one fixed mode for everything</cite> — maps well onto your layered gate: low-risk projects/stages could eventually auto-snapshot-and-flag, while schema-breaking changes always stop and ask, exactly as you've already decided.
- **Avoid, explicitly:** multi-surface sprawl. Don't add a "Manager View," multiple concurrent agent panes, or configurable automation triggers beyond the snapshot trigger. Your fixed 5-project cap and fixed 3-tool MCP surface are the correct countermeasure to exactly this failure mode — protect them as hard constraints, not defaults to be relaxed later.

### Backup/versioning — git and snapshot tools

The research here converges less on a specific tool and more on a trust condition: a backup system is trusted when restoring from it is at least as fast and as low-ceremony as the action that might require it. This is the same principle LaunchDarkly's kill switch relies on — <cite index="37-1">a kill switch is trusted specifically because toggling it off takes effect within a couple hundred milliseconds with no deployment and no downtime</cite>. The corollary for your snapshot service: if restoring a snapshot ever requires the developer to manually locate a zip, unpack it, and reconcile it against current state by hand, they will stop trusting it and start manually double-checking before risky changes — which is exactly the anxious, ad hoc behavior the snapshot service exists to remove.

- **Borrow:** "restore is a single, fast, obvious action" as a hard requirement, not a stretch goal — pair every automatic snapshot with a one-click restore path shown right next to the red dot that triggered it.
- **Adapt:** git's model of cheap, frequent, content-addressed snapshots (rather than infrequent, large, manually-triggered ones) suggests your zip-on-trigger approach should lean toward *more frequent, smaller, cheap snapshots* tied to gate events, not just to major milestones.
- **Avoid:** treating snapshotting as a background feature the user never has to look at. If it's invisible when things go well, the first time it matters is also the first time the developer learns whether they trust it — surface snapshot history somewhere in the UI even when nothing has gone wrong, the same way git log is always available even when you never need `reset --hard`.

## 3. Architecture recommendations for clean separation

The research above supports a layered architecture that maps closely to what you've already sketched, with a few sharpened boundaries:

1. **Manifest format is the seam, not the code.** Every lesson from Backstage says the catalog schema is the thing that outlives implementations. Define the per-project manifest (stages, current state, gate-layer results, snapshot pointers) as a versioned, documented JSON schema *independent of* the MCP server and Electron app. Both should be clients of that schema, not owners of it. This is what lets the Electron UI be swapped for a web UI later without touching gate logic — the gate only ever reads/writes the manifest, never talks to the UI directly.

2. **The gate is a pure function over the manifest + a proposed change, with layers as a pipeline.** Model each layer (build/tests, dependency/version, schema/type) as an independent, composable check with a common interface (`input: proposed change + current manifest state` → `output: pass / fail / needs-human, with a structured reason`). This is exactly the CI-gate lesson: fast checks first, slower/more authoritative checks later, each independently swappable, so adding layer 3 later never requires touching layer 1 or 2's code — only the pipeline's ordering.

3. **MCP tools are the only write path, and the permission split you've already defined is the correct enforcement point.** `get_status`/`validate_change` as read-only, freely callable; `record_progress` as the sole write tool, always human-confirmed. This single design choice is what structurally prevents the Backstage failure mode (stale hand-edited metadata) and the Antigravity failure mode (unsupervised destructive writes) at the same time — worth stating explicitly to yourselves as the load-bearing decision in the whole system, because everything else is arguably in service of protecting it.

4. **Snapshot service is a subscriber to gate events, not a component the gate calls directly.** Have gate-layer transitions (especially anything approaching layer 3) emit an event; let the snapshot service listen and act independently. This keeps "additive, always-safe-to-fire-automatically" cleanly separated from "the thing that decides if a change is allowed," so you could change snapshot triggers or retention policy without ever touching gate logic, and vice versa.

5. **The Electron UI is a renderer of manifest + gate state, nothing more.** No business logic in the UI layer beyond "read the manifest, render cylinders/bands/meniscus/dots, send confirm/reject for pending `record_progress` requests back through MCP." This is what makes a future web UI or CLI a matter of writing a new renderer against the same manifest schema, not a rewrite.

## 4. Usability / retention recommendations (solo-developer specific)

The task-board research is the most directly transferable material here, because your core risk — a system that gets built with enthusiasm and then quietly stops being updated — is *exactly* the Notion-vs-Linear failure mode, just for infrastructure instead of tickets.

- **Make the confirm step the only step.** Since most updates originate from an AI session proposing a `record_progress` call, the human's entire interaction is (ideally) one confirmation click or keystroke. Protect that ruthlessly — no intermediate forms, no "add a note" field that becomes mandatory over time. The Linear/Notion research is unambiguous that update friction, not tool power, is what determines whether a tracker gets kept.
- **Show the cost of not confirming.** If a proposed change sits unconfirmed, the cylinder should visibly show "pending" (e.g., a distinct band pattern or a pulsing meniscus) rather than silently doing nothing — this borrows the "alerting/prioritization" gap that Backstage's own postmortems identify as a top adoption killer: <cite index="3-1">without proper alerting, users get overwhelmed by data with no signal about what needs attention</cite>. You don't want that failure mode inverted into "the tracker has no signal at all when it's waiting on you."
- **Let the AI update tracker as a side effect of work already happening, not as a separate chore.** The pattern to avoid is any workflow where "update the tracker" is a distinct task the developer has to remember to do outside their normal working session — that's the standup-meeting problem in miniature. Since your MCP tools are already meant to be called by whatever AI session is doing the actual work, keep it that way: the tracker updates because the work happened, not because someone remembered to log it.
- **Resist configurability by default.** Every abandoned-tool retrospective above blames flexibility that was rarely used. Ship the stage-definition format as simple, plain, and slightly opinionated (an ordered list with names) rather than a rich schema with types, colors, icons, and metadata from day one — add richness only when a specific real need shows up, the same lesson as the Notion user who never touched 70% of what they'd built.
- **Restore has to be as fast as the panic that triggers it.** Per the backup-trust research, make "restore this snapshot" a single visible action next to any red dot, not a separate tool or a manual unzip.

## 5. Risks and failure modes, stated plainly

- **The gate itself could become the thing that gets bypassed.** Every CI/pre-commit source above converges on this: slow or naggy gates get routed around (`--no-verify`, disabling hooks, ignoring warnings). If layer 1 (build/tests) is slow on a real project, you will be tempted to skip `validate_change` "just this once," which quietly recreates the exact failure mode (state drifting from reality) that this whole system exists to prevent. Budget real engineering time to keep layer 1 fast, or the gate is decorative.
- **Human-confirmation fatigue.** `record_progress` requiring confirmation every time is correct in principle, but if AI sessions call it frequently (e.g., after every small step rather than meaningful milestones), the confirmation becomes a rubber-stamp the developer clicks without reading — which defeats its purpose just as surely as removing it would. You'll need a convention (probably: confirm at stage-completion granularity, not sub-task granularity) that isn't obvious from the current spec and is worth deciding explicitly.
- **Per-project stage schemas could quietly become a mini-DSL.** "Each project defines its own ordered stage list" is the right call, but the moment stages need conditions, weights, or sub-stages (which will feel tempting once you have two dissimilar real projects to track), you're one step from reinventing a workflow engine — the exact scope creep that made Backstage and Notion heavy. Worth deciding now what a stage is *not allowed* to have.
- **Snapshot volume vs. the "5 project" simplicity goal.** Frequent, cheap snapshots (recommended above) are good for trust but bad for disk usage on a personal machine if retention isn't bounded from day one. This is a small technical risk but an easy one to forget until a project folder is unexpectedly large.
- **The visual metaphor's legibility at the edges.** Stacked immiscible bands communicate ordered dependency well when a project has 3–6 clean stages. It's untested how well it reads with very short stage lists (2 stages looks like a plain progress bar, losing the metaphor's value) or oddly uneven stages (a huge "engine" stage next to a tiny "release" stage will visually misrepresent effort vs. completion). Worth prototyping with your actual Skiba Tables stage breakdown before assuming the metaphor generalizes.
- **This is still a single point of failure for exactly the problem it's solving.** If the manifest file itself is corrupted, lost, or drifts from the real repo state, you've recreated the original Skiba Tables problem one layer up — except now with more moving parts (gate, MCP server, snapshot service) between the human and the truth. The snapshot service is your mitigation here, but it means the snapshot service is arguably the single most safety-critical component in the system, more than the gate itself — worth treating its reliability as the top engineering priority, not a later add-on.

## 6. Naming note (secondary)

The closest one-line description that emerged from this research is **"a personal Backstage with a write lock"** — a catalog for one developer's own projects, where the thing Backstage never enforced (a validated, gated write path) is the actual point. If you want a name in the lab-glassware register rather than a developer-portal register, something like **Meniscus** (the exact measurement line your progress indicator is modeled on) captures the precision-instrument framing better than a generic "tracker" name would, and stays consistent with the chemistry metaphor already driving the visual design.
